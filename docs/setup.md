# Setup Guide

## Manual Setup

**Requirements**: You must be a repository admin to complete these steps.

1. Install the Droid GitHub app to your repository: https://github.com/apps/factory-droid
2. Add `FACTORY_API_KEY` to your repository secrets. You can generate an API key at https://app.factory.ai/settings/api-keys
3. Copy the workflow files from [`.github/workflows/droid.yml`](../.github/workflows/droid.yml) and [`.github/workflows/droid-review.yml`](../.github/workflows/droid-review.yml) into your repository's `.github/workflows/`

## Security Best Practices

**⚠️ IMPORTANT: Never commit API keys directly to your repository! Always use GitHub Actions secrets.**

To securely use your Factory API key:

1. Add your API key as a repository secret:

   - Go to your repository's Settings
   - Navigate to "Secrets and variables" → "Actions"
   - Click "New repository secret"
   - Name it `FACTORY_API_KEY`
   - Paste your API key as the value

2. Reference the secret in your workflow:
   ```yaml
   factory_api_key: ${{ secrets.FACTORY_API_KEY }}
   ```

**Never do this:**

```yaml
# ❌ WRONG - Exposes your API key
factory_api_key: "fk-..."
```

**Always do this:**

```yaml
# ✅ CORRECT - Uses GitHub secrets
factory_api_key: ${{ secrets.FACTORY_API_KEY }}
```

This applies to all sensitive values including API keys, access tokens, and credentials.
We also recommend that you always use short-lived tokens when possible

## Setting Up GitHub Secrets

1. Go to your repository's Settings
2. Click on "Secrets and variables" → "Actions"
3. Click "New repository secret"
4. For authentication, choose one:
   - API Key: Name: `FACTORY_API_KEY`, Value: Your Factory API key (starting with `fk-`)
5. Click "Add secret"

### Best Practices for Authentication

1. ✅ Always use `${{ secrets.FACTORY_API_KEY }}` in workflows
2. ✅ Never commit API keys or tokens to version control
3. ✅ Regularly rotate your API keys and tokens
4. ✅ Use environment secrets for organization-wide access
5. ❌ Never share API keys or tokens in pull requests or issues
6. ❌ Avoid logging workflow variables that might contain keys

## Review UX v2 permissions and defaults

Use this permission block for a mention workflow that supports review and fix:

```yaml
permissions:
  contents: write
  pull-requests: write
  issues: write
  id-token: write
  actions: read
  checks: write
```

- `contents: write` is needed for fix/report publishing. Use `contents: read` and `fix_mode: off` for review-only workflows.
- `pull-requests: write` writes summary comments, reviews, replies, and thread resolutions.
- `checks: write` belongs to the **caller workflow token**. It does not broaden the Factory App token. Missing check permission warns once and degrades without failing the review.
- `id-token: write` is required for default Factory App authentication. A supplied `github_token` must have its own necessary permissions.
- Keep checkout `persist-credentials: false`. A model step does not need publishing credentials. Token withholding is hygiene, not an OS sandbox; code and tools still run as the job user.
- Require the `Droid Review` check in branch protection if you want `fail_on_severity` or security thresholds to block merging. Droid never approves or requests changes.

The default surface is one sticky comment with a verdict and linked findings, image badges with alt text, AI-agent prompt blocks, and a clean-review message. Lifecycle reactions are eyes, hooray, and confused, never thumbs feedback. Reviews are incremental by default; the validator confirms fixes before automatic thread resolution. Generated/lock files are excluded and recorded in review details.

See the [effective-default table and base configuration example](../README.md#review-ux-inputs). Configuration precedence is built-in defaults, immutable base-branch `.factory/review.yaml`, then explicit nonempty workflow inputs. Explicit `false` and `0` override the file. An empty config-enabled input inherits; `off` clears a priority gate and `[]` clears a list. Labels are not a supported trigger; `label_trigger` is retained only as an unsupported legacy input.

## Preview and offline validation

The examples are generated from structured fixture JSON, not posted to a live PR:

```bash
bun run scripts/preview-review.ts docs/review-ux-preview.md
bun test
bun run typecheck
bun run format:check
```

[Rendered examples](review-ux-preview.md) include findings, clean, in-progress, failed, skipped and re-review summaries; inline comments; stale review bodies; check summaries; and full-security report indexes. The preview validates balanced details/fences, nonempty sections, badges, count pluralization, and marker roundtrips.

No live PR/MR test is required or performed by this workflow change. API tests mock the provider boundary. External badge rendering and GitLab instance-specific Markdown sanitization still depend on the host; choose `review_badges: emoji` or `text` if external images are blocked.
