# Code review UX research and delivery status

The original analysis below is preserved in full as source text. Historical competitor behavior and proposals are not release promises. The decisions and status table here override superseded proposals.

## Delivery decisions

- Droid never approves or requests changes. Only check/status thresholds block merging.
- Lifecycle reactions are eyes while running, hooray (GitLab tada) when clean, and confused on failure. No thumbs feedback prompts, reaction-based feedback reads, learnings, or `@droid remember` are added.
- The default summary is one sticky comment/note. Description mode is optional and preserves author-owned text.
- Severity badges use shields.io static images with meaningful alt text, with emoji and text fallbacks. A Factory-hosted dark/light badge service is not required for this release.
- `@droid fix` defaults to an authorized source-branch commit, otherwise an authorized stacked PR/MR. Default branches, unsafe destinations, inaccessible forks, and force-pushes are forbidden.

## Implementation status

Review UX v2 is implemented in this draft stack, not merged or released. Local tests, typechecks, formatting, and independent fixture-based acceptance cover the final implementation. Validation uses fixtures and local mocked APIs, never live PR/MR posts or pushes.

### GitLab portability

The GitLab component uses the shared renderer/schema/markers with MR notes and discussions, immutable GitLab permalinks, incremental comparisons, dismissal/fix state, commit statuses, and lifecycle awards. A bundled authenticated same-project note-to-pipeline bridge enables commands; it verifies actual note authorship and active Developer-or-higher membership. Full-security audits create deterministic indexed report MRs. Fix publishing separately verifies the actor and token in the actual source project and rejects default branches and concurrent updates.

True platform differences remain explicit: no native note-triggered CI, no neutral status or check-run Markdown text/step-log API, no GitHub review object to mark stale, no GitHub step-summary file, and host-dependent HTML/alert rendering. The bundled bridge refuses forks rather than exposing target-project secrets to fork code; a safe cross-fork snapshot route is not shipped. GitLab native pipeline event types also do not expose every GitHub action, so automatic policies infer opened on first review and synchronize afterward. See [GitLab setup](gitlab-setup.md#platform-differences).

The nit catalogue Small things competitors get right that make the output feel finished. Grouped by surface.  Typography and wording  Use · (middle dot) between footer fields; never ——. Use … (single character) in progress text, consistently. Sentence case titles, no trailing period, under ~70 characters. Outcome-phrased titles ("Users can't unpin long-titled sessions") beat mechanism titles ("Missing length check"). Pluralize every count correctly (Greptile ships "1 comments"; don't). Escape markdown in model-written titles that are interpolated into links or tables (|, [, ]). Short SHAs in backticks: 7 characters in prose, full SHA in links. Use <relative-time datetime="…"> for "Running since" so GitHub renders "2 minutes ago". One consistent product name: "Droid" (not "Droid Exec", "droid", "Factory Droid" in different places). Don't say "task" for a review; say "reviewed this PR". Layout  Verdict as ### heading, not bold text, so it shows in GitHub's outline. <details open> for the open findings list, collapsed for everything else. <sub> for footers and feedback prompts so they recede. GitHub alerts with intent: [!NOTE] in progress, [!IMPORTANT] skipped, [!WARNING] failed or rate limited, [!CAUTION] blocking findings. Empty sections are omitted, never rendered as "None". Tables: left-align text, center-align counts (:-:). Insert zero-width spaces after / in long file paths inside tables so they wrap (Copilot trick). Keep the in-progress banner above the previous review instead of wiping it. Badges and images  <picture> with prefers-color-scheme dark/light sources; explicit height and align="top" so badges sit on the text baseline. Meaningful alt text (P1, Security) so the comment reads correctly without images and in email notifications. Version query string on asset URLs (?v=2) for cache busting when restyling. Wrap a badge in <a href="#"> only if we want to block GitHub's image click-through (Greptile does this). Fallback to emoji (🔴 🟠 🟡) when review_badges: emoji is set, for GHES installs that block external images. Links  Every finding in the summary links to its #discussion_r… thread. Code references outside the diff use full-SHA permalinks with a line range, so GitHub renders an inline snippet. "View job" links to the specific job, not just the run, when the job id is available. Compare/"Create PR" links prefill title and body. Hidden markers (machine layer)  <!-- droid-review-summary:v1 --> on the sticky comment. <!-- droid-review-state:v1 {json} --> for incremental memory. <!-- droid-review:v1 head=<sha> [stale] --> on review bodies. <!-- droid-finding:v1 {json} --> on each inline comment (id, severity, category, head). <!-- droid-severity: {json} --> in the check run text for merge gates. Version every marker (:v1) so formats can evolve without breaking old PRs. Behaviour  Remove 👀 when done; a reaction left behind looks like a hung run (Claude's docs warn about exactly this). Never post a top-level comment per run; edit the sticky one. Never repost a finding a human resolved (Copilot's documented weakness). Don't review drafts automatically unless configured; say so when skipping on a manual trigger. Skip generated and lock files by default and list them under "Review details". Redact secrets in every rendered error and prompt. Keep the agent-prompt blocks fenced with ~~~ so nested backticks survive copy-paste. 8.
